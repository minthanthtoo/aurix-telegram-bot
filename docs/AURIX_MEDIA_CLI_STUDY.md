# AuriX media generation CLI study

Date: 2026-09-13 (Asia/Rangoon)

## Boundary

The command-line implementation should use documented API surfaces, not private
ChatGPT or Google Flow browser internals. Browser bundles, session cookies, and
undocumented frontend endpoints are unstable, account-bound, and unsuitable for
an AuriX product integration.

Use these public routes instead:

- OpenAI image generation: `POST /v1/images/generations`.
- OpenAI video generation: `POST /v1/videos`, then poll and download content.
- Google video generation: Gemini API Veo `generate_videos`, then poll the
  long-running operation and download the result.
- AuriX image/video generation: existing OpenAI-compatible gateway routes
  `GET /v1/models`, `POST /v1/images/generations`, `POST /v1/videos`,
  `GET /v1/videos/{video_id}`, and `GET /v1/videos/{video_id}/content`.

Sources checked:

- OpenAI API Reference, Videos:
  https://platform.openai.com/docs/api-reference/videos
- OpenAI API Reference, Models:
  https://platform.openai.com/docs/api-reference/models
- OpenAI data controls by endpoint:
  https://platform.openai.com/docs/models/default-usage-policies-by-endpoint
- Google AI for Developers, video generation:
  https://ai.google.dev/gemini-api/docs/video
- Google AI for Developers, Veo 3.1:
  https://ai.google.dev/gemini-api/docs/veo

## Existing AuriX implementation

The repo has a production-grade image path and a first-pass video gateway:

- `aurix_ai/router.py` contains `NineRouterClient`, an OpenAI-compatible
  standard-library HTTP client with JSON, raw-byte, streaming chat, and model
  discovery helpers.
- `aurix_ai/web_api.py` exposes first-party browser routes
  `/api/image-models` and `/api/images/generations`.
- `aurix_ai/web_api.py` also exposes external API routes `/v1/models` and
  `/v1/images/generations`, including a gateway-specific binary extension:
  `/v1/images/generations?response_format=binary`.
- `aurix_ai/web_api.py` exposes external video routes `/v1/videos`,
  `/v1/videos/{video_id}`, and `/v1/videos/{video_id}/content` as an
  authenticated pass-through to the configured upstream router.
- `aurix_ai/api_keys.py` enforces account scopes and records usage. Image
  requests use mode `image_generation`; video submit requests use mode
  `video_generation`.
- `web/ai-app/app.js` already implements browser image mode, image model
  discovery, size selection, prompt submission, and image preview rendering.

That means a CLI should not call the first-party browser routes. It should act
like a partner backend and use the external `/v1/*` routes with an AuriX-issued
API key.

## Added CLI

The new `scripts/aurix_media_cli.py` provides:

```sh
python scripts/aurix_media_cli.py --api-key "$AURIX_AI_API_KEY" \
  models --capability image_generation
```

```sh
python scripts/aurix_media_cli.py --api-key "$AURIX_AI_API_KEY" \
  image \
  --model image-model-id \
  --prompt "A cinematic sunrise over a quiet mountain lake, natural colors" \
  --size 1024x1024 \
  --output image.png
```

```sh
python scripts/aurix_media_cli.py --api-key "$AURIX_AI_API_KEY" \
  image \
  --model image-model-id \
  --prompt "A clean product photo on a white table" \
  --binary \
  --output image.webp
```

For official video providers, the CLI also provides direct, non-browser
commands:

```sh
python scripts/aurix_media_cli.py --api-key "$AURIX_AI_API_KEY" \
  video \
  --model video-model-id \
  --prompt "A cinematic 4 second product reveal on a clean tabletop" \
  --seconds 4 \
  --size 1280x720 \
  --output product-reveal.mp4
```

```sh
OPENAI_API_KEY=sk_... python scripts/aurix_media_cli.py \
  openai-video \
  --model sora-2 \
  --prompt "A cinematic 4 second product reveal on a clean tabletop" \
  --seconds 4 \
  --size 1280x720 \
  --output product-reveal.mp4
```

```sh
GEMINI_API_KEY=... python scripts/aurix_media_cli.py \
  gemini-veo \
  --model veo-3.1-generate-preview \
  --prompt "A cinematic 8 second product reveal on a clean tabletop" \
  --aspect-ratio 16:9 \
  --resolution 720p \
  --output product-reveal.mp4
```

Environment variables:

- `AURIX_AI_BASE_URL`, default `https://ai.aurix-mart.tech`
- `AURIX_AI_API_KEY`, used when `--api-key` is omitted
- `OPENAI_API_KEY`, used by `openai-video`
- `GEMINI_API_KEY`, used by `gemini-veo`

## Video expansion design

Video is implemented as a job API, not copied from the image route one-to-one.
OpenAI video generation and Google Veo are asynchronous:

1. Submit a prompt and optional reference assets.
2. Receive a job or operation ID.
3. Poll status until completion or failure.
4. Download generated bytes.
5. Record request, provider job ID, status, model, account, and output location.

Implemented AuriX route shape:

- `GET /v1/models` includes models with capability `video_generation`.
- `POST /v1/videos` starts a video job.
- `GET /v1/videos/{video_id}` returns normalized job status.
- `GET /v1/videos/{video_id}/content` streams the completed media bytes.

Recommended CLI shape:

```sh
python scripts/aurix_media_cli.py video \
  --model video-model-id \
  --prompt "A cinematic 8 second product reveal" \
  --seconds 8 \
  --size 1280x720 \
  --output video.mp4
```

```sh
python scripts/aurix_media_cli.py gemini-veo \
  --model veo-3.1-generate-preview \
  --prompt "A cinematic 8 second product reveal" \
  --aspect-ratio 16:9 \
  --resolution 720p \
  --output video.mp4
```

Future expansion should normalize provider-specific options such as
`aspectRatio`, `resolution`, reference images, first/last frame, extension
video, and operation polling behind the same job lifecycle.

## Model discovery rule

Always discover capabilities first. Do not assume a chat model can generate
images or video. The browser sample and this CLI both need the same invariant:
model selection is capability-gated and account-scoped before provider quota is
spent.
